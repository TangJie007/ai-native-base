# RFC 2119 关键词用法

本文件规范 Requirement 中的强度词使用。规范来源：[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)。

## 1. 四个关键词

### MUST / MUST NOT

**强度**：绝对要求。

- 违反即错误。
- 不允许有例外，除非 Requirement 本身有明确的豁免条款。

**示例**：

```
系统 MUST 拒绝未通过 2FA 的用户登录。
用户密码 MUST NOT 以明文存储。
```

**何时使用**：

- 涉及**安全**（认证、授权、加密）
- 涉及**数据完整性**（事务、一致性）
- 涉及**合规**（法律、法规、行业标准）
- 涉及**用户明确承诺**（如 SLO、SLA）

### SHALL / SHALL NOT

**强度**：强推荐。

- 必须满足，除非有明确说明的例外。
- 与 MUST 的区别：**允许在特定条件下破例**，但需要文档化理由。

**示例**：

```
系统 SHALL 在用户会话过期时提示用户重新登录，除移动 App 的会话管理外。
日志 SHALL NOT 包含用户 PII，除调试日志且已启用匿名化过滤。
```

**何时使用**：

- 大部分产品行为契约
- 有合理例外的功能要求
- 团队达成共识但仍需文档化的规范

### SHOULD / SHOULD NOT

**强度**：建议。

- 建议满足，例外不需要说明理由。
- 违反不会导致错误，但可能引发评审讨论。

**示例**：

```
系统 SHOULD 在错误响应中包含 request_id 便于排查。
UI SHOULD NOT 使用浏览器默认的红色错误提示（除非项目品牌要求）。
```

**何时使用**：

- 最佳实践
- 用户体验建议
- 性能建议（非关键路径）
- 一致性建议

### MAY

**强度**：可选。

- 完全可选，实现者自行判断。
- 描述"允许的能力"而非"要求的能力"。

**示例**：

```
系统 MAY 支持多语言。
用户 MAY 在设置中关闭个性化推荐。
```

**何时使用**：

- 未来扩展的伏笔
- 明确"不承诺"的能力
- 用户可自定义的行为

## 2. 使用决策

选词前问 3 个问题：

```
Q1：违反这个要求会是什么后果？
├─ 系统故障 / 数据损坏 / 安全事故 → MUST
├─ 用户体验受损 → SHALL
├─ 只是不优雅 → SHOULD
└─ 无关紧要 → MAY

Q2：是否有合理的例外？
├─ 无 → MUST
├─ 有但需文档化 → SHALL
├─ 有且不需要说明 → SHOULD
└─ 完全取决于实现者 → MAY

Q3：是否影响合规或 SLA？
├─ 是 → MUST
└─ 否 → 参考 Q1、Q2
```

## 3. 常见错误

### ❌ 过度使用 MUST

```
系统 MUST 支持手机号验证码登录。    # 应该是 SHOULD（若这是新方向）
MUST 使用 JWT 作为 token 格式。      # 应该是 SHOULD（除非合规要求）
```

**问题**：MUST 会让 spec 变得脆弱，每次技术选型都要重新谈判。

### ❌ 应该用 MUST 却用了 SHOULD

```
系统 SHOULD 拒绝未通过 MFA 的登录。  # 应该是 MUST（安全要求）
SHOULD 在事务中锁定相关行。          # 应该是 MUST（数据完整性）
```

**问题**：安全的 SHOULD 会被实现者忽视，导致漏洞。

### ❌ 用 SHALL 但没写例外

```
系统 SHALL 使用 HTTPS。              # 但没说本地开发环境
SHALL 记录所有 SQL 语句。            # 但没说日志保留时长
```

**问题**：SHALL 的价值在于允许例外，若没写例外，等于 MUST。

### ❌ MUST 与 SHOULD 混用描述同一件事

```
系统 MUST 支持国际化。
系统 SHOULD 支持多语言。
```

**问题**：MUST 与 SHOULD 应描述**同一件事**的不同强度，或**不同的事**。

## 4. 上下文建议

| 场景 | 关键词 |
|------|--------|
| 安全要求 | MUST |
| 数据完整性 | MUST |
| 合规要求 | MUST |
| 核心产品行为 | MUST |
| 用户体验关键路径 | SHALL |
| 团队约定的实现规范 | SHALL |
| 性能建议（非关键） | SHOULD |
| 一致性与风格 | SHOULD |
| 可选能力 | MAY |
| 未来扩展伏笔 | MAY |

## 5. 与 Scenario 的关系

Requirement 中的 MUST 会在 Scenario 中被验证：

- **MUST** → 违反 Scenario 就是缺陷
- **SHALL** → 违反 Scenario 需要 review
- **SHOULD** → 违反 Scenario 可接受
- **MAY** → Scenario 描述"允许的行为"，非"要求的行为"

**示例**：

```
### REQ-1: 验证码发送
系统 MUST 在验证码过期后拒绝登录。

#### SC-1.1: 过期验证码
- **GIVEN** 验证码已过期 5 分钟以上
- **WHEN** 用户 POST /api/auth/sms-login { phone, code }
- **THEN** 接口 MUST 返回 HTTP 401
```

Scenario 中的 MUST/SHALL 应与父 Requirement 强度一致，或更严格，不能更弱。

## 6. 中文表达

本 skill 的 Requirement 建议用**英文关键词 + 中文正文**的混合表达：

```
系统 MUST 在验证码过期后拒绝登录。
```

不要用中文关键词：

```
系统必须拒绝登录。   # ❌ 不用
系统一定要拒绝登录。  # ❌ 不用
```

保持 MUST / SHALL / SHOULD / MAY 原文，与 RFC 2119 对齐，便于工具化处理。

## 7. 快速检查表

写 Requirement 前：

- [ ] 关键词是否与要求强度匹配？
- [ ] 若用 SHALL，是否明确了例外？
- [ ] 若用 SHOULD，是否意识到可能被违反？
- [ ] 若用 MAY，是否明确这是可选能力？
- [ ] 关键词是否一致（不混用）？

写完 Requirement 后：

- [ ] 是否可以测试（是否有 Scenario 验证）？
- [ ] 是否避免模糊词（"快速"、"高效"、"友好"）？
- [ ] 是否可执行（实现者能理解要做什么）？
