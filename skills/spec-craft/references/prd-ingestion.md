# PRD 抽取策略

本文件定义如何从各种形态的 PRD 中抽取 Requirement 与 Scenario，是 `01-explore` 与 `02-propose` 阶段的核心方法论。

## 1. PRD 输入形态

不同的 PRD 形态有不同的抽取难度：

| 形态 | 示例 | 抽取难度 | 抽取策略 |
|------|------|---------|---------|
| **结构化 PRD** | 正式需求文档，含 REQ 编号 | 低 | 直接映射 |
| **用户故事** | As a ... I want ... So that ... | 中 | 转成 Requirement + Scenario |
| **会议纪要** | 混杂讨论，含多种意见 | 高 | 先梳理决策，再抽取 |
| **表格 / Excel** | 功能点列表、字段列表 | 中 | 逐行转 Requirement |
| **聊天记录** | IM 中的碎片化讨论 | 高 | 先归类，再抽取 |
| **图片 / 原型** | UI mockup、白板照片 | 高 | 需口述配合 |
| **口述** | 用户直接说 | 高 | 边聊边抽 |

## 2. 抽取规则（语义映射）

不同 PRD 内容映射到不同 artifact：

| PRD 内容 | 落点 |
|---------|------|
| **背景 / 目标 / 用户价值** | `proposal.Intent` |
| **功能点 / 业务规则** | `Requirement`（写入 delta） |
| **边界 / 异常 / 数值限制** | `Scenario`（GIVEN/WHEN/THEN） |
| **不做 / 后续版本** | `proposal.Out` / `Non-Goals` |
| **未明确** | `[待确认]` 标注，**不编造** |

## 3. 抽取流程

### 步骤 1：识别 PRD 形态

先判断输入属于哪类形态，选择对应策略。

### 步骤 2：粗抽取

先不做精细映射，把 PRD 中的每个"点"抄录下来，标注初步类型：

```
[背景] 当前用户登录只能用邮箱+密码，用户体验差
[功能] 支持手机号 + 6 位验证码登录
[边界] 验证码有效期 5 分钟
[边界] 每分钟最多发送 1 次
[疑问] 是否支持国际手机号？
[不做] 本版本不支持第三方 OAuth 登录
```

### 步骤 3：语义分类

对每个点判断：

- **背景** → `proposal.Intent`
- **功能** → 转为 `Requirement`
- **边界** → 转为 `Scenario` 的 GIVEN / THEN
- **疑问** → 加入 `change.yaml.open_questions`
- **不做** → `proposal.Out` 与 `Non-Goals`

### 步骤 4：转写为 spec 格式

按 `spec-format.md` 的规范转写：

```
原始 PRD:
  支持手机号 + 6 位验证码登录，验证码有效期 5 分钟，每分钟最多发送 1 次

抽取后:

### REQ-auth.sms-login.1: 发送验证码
系统 MUST 支持向指定手机号发送 6 位验证码，有效期 5 分钟。

#### Scenarios
##### SC-1.1: 正常发送
- GIVEN 手机号格式合法
- WHEN 用户 POST /api/auth/sms-send { phone }
- THEN 接口 MUST 返回 HTTP 200
- AND THEN 短信内容 MUST 包含 6 位数字
- AND THEN expiresAt MUST 为当前时间 + 5 分钟

##### SC-1.2: 频率限制
- GIVEN 该手机号 60 秒内已发送过验证码
- WHEN 用户再次 POST /api/auth/sms-send
- THEN 接口 MUST 返回 HTTP 429
```

### 步骤 5：抽取疑问清单

用 `[?]` 标注，累积到 `change.yaml.open_questions`：

```yaml
open_questions:
  - id: Q1
    question: 是否支持国际手机号（+852、+81 等）？
    asked_at: 2026-10-04
    answered: false
  - id: Q2
    question: 用户已注册邮箱账号后，能否绑定手机号？
    asked_at: 2026-10-04
    answered: false
```

### 步骤 6：请用户确认

- 展示抽取结果
- 请求确认
- 未确认部分标记为 `[待确认]`

## 4. 各类形态的具体处理

### 4.1 结构化 PRD

**优势**：直接映射。

**示例**：

```markdown
# PRD: 用户认证 v2.0

## 3.1 手机号验证码登录

### REQ-3.1.1 发送验证码
- 用户提交手机号后，系统发送验证码
- 验证码格式：6 位数字
- 有效期：5 分钟

### REQ-3.1.2 验证码登录
- 用户提交手机号 + 验证码
- 验证码正确则登录成功
- 验证码错误或过期则登录失败
```

**抽取**：

- 直接用 PRD 的 REQ 编号作为 Reference
- 转为 spec-craft 的 REQ-{domain}.{atom}.{n}
- PRD 中未明确的边界，用 [待确认] 标注

### 4.2 用户故事

**格式**：`As a <role>, I want <goal>, So that <value>.`

**示例**：

```markdown
As a 首次访问的用户，我想用手机号验证码登录，
以便不用记密码。
```

**抽取**：

```
Requirement:
系统 MUST 支持手机号验证码登录（用于新用户注册与老用户登录）。

Scenario:
- GIVEN 用户是首次使用系统（不存在账号）
- WHEN 用户完成手机号 + 验证码登录流程
- THEN 系统 MUST 自动创建用户账号
- AND THEN 用户进入已登录状态
```

**关键**：从 "I want" 抽取 Requirement，从 "So that" 与隐含边界抽取 Scenario。

### 4.3 会议纪要

**问题**：混杂决策、讨论、异议，需要梳理。

**处理流程**：

1. **识别决策**：找"决定"、"确认"、"OK"、"就这个"等关键词
2. **过滤讨论**：删除"或许可以"、"我们再想想"、"这个先不讨论"
3. **标注异议**：把"但 XXX 反对"、"这里有点问题"记入 open_questions
4. **抽取最终决议**：只保留被确认的决策

**示例**：

```markdown
会议纪要（原始）：
- 讨论了手机号登录方案
- A 说可以，B 有点担心成本
- C 提出用邮箱验证码也可以
- 最后决定：本版本只做手机号验证码，邮箱验证码下版本再说
- 后续：短信服务商选型下周讨论
```

**抽取**：

```
[功能] 本版本支持手机号 + 6 位验证码登录
[不做] 邮箱验证码（延后到下版本）
[疑问] 短信服务商未定，成本担忧
[疑问] 是否需要考虑多语言（会议纪要未提）
```

### 4.4 表格 / Excel

**问题**：字段丰富但语义不连贯。

**处理**：

- 一行 = 一个功能点 → 转一个 Requirement
- 列包含"字段名、类型、必填" → 转 Scenario 的 THEN 断言
- 列包含"业务规则" → 转 Scenario 的 WHEN / THEN

**示例**：

```
| 字段 | 类型 | 必填 | 规则 |
|------|------|------|------|
| 手机号 | string | 是 | 11 位数字 |
| 验证码 | string | 是 | 6 位数字 |
| 有效期 | int | - | 300 秒 |
```

**抽取**：

```
Requirement: 系统 MUST 支持手机号验证码登录。

Scenario:
- GIVEN 手机号为 11 位数字
- GIVEN 验证码为 6 位数字且未过期
- WHEN 用户提交登录请求
- THEN 系统 MUST 验证通过后返回登录态

Scenario:
- GIVEN 手机号不是 11 位数字
- WHEN 用户提交登录请求
- THEN 系统 MUST 返回 HTTP 400 与 E_INVALID_PHONE
```

### 4.5 聊天记录

**问题**：最碎片化，信息散布在不同消息中。

**处理**：

1. **时间序整理**：按时间顺序排列
2. **主题聚类**：把相关消息归到一起
3. **决策定位**：找"确认"、"OK"、"就这么办"
4. **抽取最终结论**：只保留被最终确认的部分

**示例**：

```
2026-09-30 10:00  产品经理：能不能加个短信登录？
2026-09-30 10:05  开发：技术上没问题，成本要算下
2026-09-30 10:15  产品经理：一条短信几分钱，一年几万用户吧
2026-09-30 10:30  开发：那可以，用阿里云短信
2026-09-30 10:35  产品经理：验证码多久失效？
2026-09-30 10:36  开发：一般 5 分钟，你觉得呢？
2026-09-30 10:37  产品经理：5 分钟可以
2026-09-30 10:40  开发：那我们就用 5 分钟
```

**抽取**：

```
[决策] 支持手机号 + 6 位验证码登录
[决策] 用阿里云短信
[决策] 验证码有效期 5 分钟
[疑问] 短信频率限制未定
[疑问] 手机号格式（国际 vs 国内）未定
[疑问] 成本控制策略未定
```

### 4.6 图片 / 原型

**问题**：视觉信息，需口述配合。

**处理**：

1. **让用户描述关键交互**：不要猜
2. **关注状态变化**：什么状态能触发什么操作
3. **抽取边界**：报错提示、边界值
4. **UI 与行为分离**：UI 布局不进 spec，行为契约进 spec

**注意**：视觉细节不属于 spec，属于 design.md 或前端代码。

### 4.7 口述

**处理**：边聊边抽。

```
用户：想加个手机号登录
Agent：明白，具体是发验证码的那种吗？
用户：对，就是短信验证码
Agent：那验证码有效期多久？
用户：5 分钟吧
Agent：好的，那如果 5 分钟内发了两次呢？
用户：限制一下吧，1 分钟 1 次
Agent：明白，那验证码错了怎么办？
用户：就是登录失败嘛
Agent：明确一点，返回什么错误码？
用户：随便一个，就说验证码不对
Agent：好，我记一下。还有吗？
用户：没有了
```

**Agent 输出**：抽取后的 spec 草稿 + 待确认项。

## 5. 待确认项处理

未明确的点用 `[?]` 标注：

```
[?] 是否支持国际手机号（+852、+81 等）？
[?] 用户已注册邮箱账号后，能否绑定手机号？
[?] 短信服务商选型待定
[?] 成本控制策略待定
```

**写入 `change.yaml.open_questions`**：

```yaml
open_questions:
  - id: Q1
    question: 是否支持国际手机号（+852、+81 等）？
    asked_at: 2026-10-04
    answered: false
    answer: null
```

**处理方式**：

- **阻塞类**：必须回答才能继续（如技术选型）
- **非阻塞类**：可以标注后继续，archive 前再回答

## 6. 与既有 atom 的关系

抽取后与既有 `specs/atom/` 对比：

| 情况 | 处理方式 |
|------|---------|
| 相同语义，全新 atom | ADDED |
| 相同语义，修改既有 atom | MODIFIED |
| 与既有 atom 冲突 | 需评审，决定是否弃用或合并 |
| 覆盖既有能力 | REMOVED，注明弃用原因 |

**示例**：

```
既有 specs/atom/auth/email-login.md 存在。
新 PRD：手机号登录。

判断：
- 是否新增 atom？  是（不同 domain 或不同认证方式）
- 与既有 email-login 有冲突吗？  否
- operation: ADDED
```

## 7. 抽取质量检查

Agent 完成抽取后自查：

### 7.1 完整性

- [ ] 所有 PRD 的功能点都抽取到了？
- [ ] 所有 PRD 的边界都抽取到了？
- [ ] 所有 PRD 的疑问都标注为 [待确认]？
- [ ] 所有"不做"的部分都列入 Non-Goals？

### 7.2 精确性

- [ ] Requirement 有 RFC 2119 关键词？
- [ ] Scenario 是 GIVEN / WHEN / THEN 结构？
- [ ] 无模糊词（快速、高效、友好、合理）？
- [ ] 有具体的可验证值（数字、字段名）？

### 7.3 一致性

- [ ] 新 atom 与既有 atom 无冲突？
- [ ] 术语与既有 atom 一致？
- [ ] 命名规范一致？

### 7.4 未编造

- [ ] 所有 [待确认] 都被标注？
- [ ] 未替用户做未确认的决定？

## 8. 检查清单

抽取完成后，Agent 应输出：

```markdown
## 我理解到的需求

<一段话概括>

## 抽取的 Requirement

### REQ-auth.sms-login.1
系统 MUST 支持手机号验证码登录。

### REQ-auth.sms-login.2
系统 MUST 支持验证码过期处理。

## 抽取的 Scenario

- SC-1.1: 正常发送
- SC-1.2: 频率限制
- SC-2.1: 新用户登录
- SC-2.2: 老用户登录
- SC-2.3: 验证码错误
- SC-2.4: 验证码过期

## 待确认项

- [?] 是否支持国际手机号？
- [?] 短信服务商未定
- [?] 成本控制策略未定

## 建议路径

Architectural（新功能，含新数据表）

## 下一步

请确认上述抽取结果。确认后我进入 /spec propose，创建 change。
```

## 9. 常见错误

### ❌ 编造未明确的部分

**症状**：PRD 只说"支持手机号登录"，agent 却写了"国际手机号需国际格式"。

**问题**：用户可能不需要国际支持。

**修复**：未明确的点一律标注 `[待确认]`，让用户决策。

### ❌ 遗漏隐含约束

**症状**：PRD 只说"支持验证码登录"，agent 忽略了频率限制、验证码有效期。

**问题**：会导致安全漏洞、成本失控。

**修复**：抽取时对常见隐含约束主动询问：

- 频率限制？
- 有效期？
- 重试次数？
- 过期处理？

### ❌ 抽取 UI 而非行为

**症状**：把"页面布局"、"按钮位置"当 spec。

**问题**：UI 属于 design 而非 spec。

**修复**：只抽取"什么操作得到什么结果"的行为契约，UI 细节留给前端实现。

### ❌ 混入实现细节

**症状**：spec 里写"用 JWT"、"用 Redis 存储验证码"。

**问题**：技术选型属于 design.md，不属 spec。

**修复**：spec 只写"需要什么行为"，不写"如何实现"。
