# 01-explore：需求澄清

## 何时进入

- 用户描述了模糊的需求（"能不能做 XXX"、"我想支持 XXX"）
- 用户提供的 PRD 里有大量 `[待确认]` 或空白
- 用户说不清要什么，只想先聊聊

## 何时不用

- 需求已经清晰，直接进 `/spec propose`
- 用户只想闲聊，没打算产出 artifact

## Iron Law

1. **本阶段不写任何文件**：不落 `specs/`，不建 change 目录，不写代码
2. **不做技术选型**：这是产品需求澄清，不是技术方案讨论
3. **不做承诺**：不写"我们一定支持 XXX"，只记录用户的诉求和已知约束
4. **不编造**：用户没说的用 `[待确认]` 标注，不假设

## 步骤

1. **确认上下文**
   - 项目背景是什么？（读项目 README 或用户说明）
   - 已有的 spec 在哪？（若有 `specs/atom/`，快速浏览相关 domain）
   - PRD 输入在哪？（用户给的路径或口述）

2. **抽取需求点**（参考 `../../references/prd-ingestion.md`）
   - 用户目标 / 用户价值
   - 明确的业务规则
   - 明确的边界与异常
   - **未明确**的部分（列成待确认清单）

3. **提问清单**
   - 按优先级列出 3-7 个关键问题
   - 每个问题只问一件事
   - 用具体选项而非开放式问题（"手机号 + 验证码，还是邮箱 + 密码，还是两者都要？"）

4. **收敛结论**
   - 用一段话复述理解到的需求
   - 列出已明确的 Requirement 骨架（草稿，不写文件）
   - 列出剩余的 `[待确认]` 项
   - 询问用户是否可以进入 propose

5. **判断路径分级**（参考 `../../references/path-tiering.md`）
   - 若只是可行性探针 → 建议走 Spike
   - 若是小改动 → 建议走 Bounded
   - 若是新功能/PRD 驱动 → 建议走 Architectural

## 输出格式（对话内）

```markdown
## 我理解到的需求

<一段话概括>

## 已明确的要点

- [REQ-1] ...
- [REQ-2] ...

## 待确认

- [?] 是否支持 XXX？
- [?] 数值范围是？
- [?] 与 YYY 的边界？

## 建议路径

Architectural / Bounded / Spike，理由：...

## 下一步

确认后我进入 `/spec propose`，创建 change。
```

## 完成判据

- 用户明确表示"理解正确"或"就这些，开始吧"
- 已建议路径分级
- **未**落任何文件
